# 服务与单次操作生命周期（Service & Attempt Process Lifetime）

**中文** | [English](service-process-lifetime.md) · [返回文档中心](README.md)

在 AI Agent 运行过程中，存在着三种寿命完全不同的执行单元：
1. **短生命周期的前台调用或 Hook**（如几百毫秒即退出的 `Stop Hook`）；
2. **按需常驻的后台领域知识服务**（`mindie-knowledge serve`，必须在短 Hook 退出后继续在后台完成脱敏、分块与索引）；
3. **后台服务发起的单次子进程调用**（如启动小模型摘要 Worker 或 Gitleaks 扫描器，一旦后台服务退出或取消，这些后代进程树必须被干净回收，绝不能变成孤儿进程）。

本文说明 `mindie-knowledge` 如何在 Windows、Linux/WSL 与 macOS 三大平台上用操作系统原生机制解决这两重生命周期控制问题。

---

## 1. 三大平台的进程容器化方案对比

| 操作系统 | 后台知识服务宿主（跨越短 Hook 存活） | 单次摘要/工具子进程树回收（防孤儿进程） |
| --- | --- | --- |
| **原生 Windows** | **Task Scheduler 按需任务**（通过原生 `pywin32` COM API 注册当前用户 SID 私有任务，运行 `pythonw.exe`） | **命名 Job Object**（挂起创建 `CREATE_SUSPENDED` + `KILL_ON_JOB_CLOSE`，即使中间层启动器退出也能杀干净孙进程） |
| **Linux / WSL** | **`systemd` 按需用户服务**（要求 `systemd 254+` 统一 cgroup 层级，`Type=exec`、`ExitType=main`、`KillMode=control-group`） | **独立进程组 + 服务 cgroup 兜底**（正常取消按进程组回收；若服务主进程崩溃，由 `systemd` 控制组自动清理全部后代） |
| **macOS** *(及无 systemd 的直接调用)* | **独立守护进程组** + 启动锁与本地回环认证 | **`owner-pipe` 管道守卫进程**（由核心持有管道唯一写端；一旦核心关闭管道或意外崩溃触发 EOF，守卫进程立即杀掉整个操作进程组） |

> [!Why]
> **为什么 macOS 不用 `launchd` 管理每次模型调用？**
> 实机验证表明，macOS `launchd` 仅回收其直接作业的进程组；若子进程开启了新会话或中间层进程提前退出，当核心意外崩溃时，独立的 `launchd` 作业仍会残留。因此，我们在 macOS 上为每次调用配了一个极轻量的 `owner-pipe` 守卫进程：只要核心进程存活，管道写端就保持打开；一旦核心退出或崩溃，内核立即关闭写端，守卫进程收到 EOF 后毫秒级清理整个进程组。

## 2. 一次性安全上下文传递（One-Use Launch Context）

当短生命周期的 Hook 唤醒后台知识服务时，需要将当前选择的配置路径与必要的环境变量（如代理 `HTTPS_PROXY` 或模型认证变量名）安全传递给服务宿主，且**绝不能把敏感值明文写进计划任务 XML 或 `systemd` Unit 属性里**：

- **Windows**：使用当前用户 **DPAPI** 加密传输文件，绑定用户 SID、配置指纹、一次性 Nonce 与工作目录；
- **Linux / POSIX**：使用当前 UID 私有的 `0600` 普通文件（拒绝软链接、FIFO 或非本人所有者）；
- **阅后即焚**：服务主进程启动后立即校验并删除该一次性传输文件，再将声明的环境变量投影到自身进程中。

## 3. 启动锁、未知状态对账与精确退役

- **串行启动与不确定状态保留**：
  启动与退役操作由同一个启动锁串行化。在请求操作系统管理器（Task Scheduler 或 `systemd`）启动服务前，先写入持久化意图。若管理器请求超时或本地回执写入失败，系统不会盲目再次发起启动，而是保留上下文并通过状态检查对账。
- **不给正常业务设武断超时**：
  短 Hook 中的状态探测预算（如 0.25 秒）仅控制前台 Hook 等待多久返回，**绝不会给后台正在运行的脱敏、索引或小模型调用强加业务截止时间**。
- **精确配置指纹与安全退役（`retire_service`）**：
  每个后台服务都绑定其完整配置指纹。当插件准备升级或空闲退出时，`retire_service` 会先检查是否有在途请求、活跃 Worker 或待处理采集：
  - 若服务正忙，拒绝退役并回滚退役标记；
  - 若服务空闲，则记录该精确配置的退役回执并安全关停，防止迟到的唤醒辅助进程把旧版本服务重新拉起。
- **可证明已被取代的注册项（Windows）**：
  在服务停止期间发生的升级会改变引擎配置，从而留下上一代指纹的启动记录与已注册任务。仅当残留同时满足「同一所有权链」（同一用户 SID、同一安装清单路径、严格的单动作任务形状）且「可证明已失活」（任务不在 Running/Queued，且存在终态回执、已死亡的记录 pid、或从未运行/已被消费的 attempt 证明动作已结束）时，对账才会将其退役——记录可见的 `stale_launch_record_retired` / `stale_registered_task_retired` 诊断，然后按新一代配置重新注册。存活的记录 pid 一票否决所有其它证据；任何身份信息不符（外部 SID、外部清单、异常任务形状）仍然以 `foreign_task` / `foreign_launch_record` 硬性失败。当 `cli stop` 面对已经死亡的端点时，会报告 `not-running` 并顺带退役这些可证明已失活的残留，而不是仅仅 RPC 失败；清理失败会与已完成的停止结果一并如实呈现，绝不静默跳过。
